# SSO audit - 2026-09-29

## Scope and verdict

Audit of commit `145fd7432e8f027f28d9535ee97f238d53f4de54`, without product changes. The SSO source and dependency paths were unchanged at `41281f16`, the main branch head when this report was prepared.

OIDC, SAML and LDAP successfully authenticated against isolated real test servers, but the implementation is not ready for unconditional acceptance. Six confirmed findings remain open. Local results do not certify Entra ID, Okta, Active Directory or production deployments.

Temporary infrastructure used a separate Docker Compose project, network, volumes, synthetic accounts and secrets. Production configuration and data were not loaded. HTTPS, LDAPS and StartTLS used a dedicated test CA with certificate verification enabled. All owned containers, volumes, networks, three newly built images and temporary secrets were removed after testing. Existing Graphify changes were preserved.

## Confirmed findings

### SSO-01 - P1: LDAP step-up has no authentication rate limit

Source: `apps/server/src/core/sso/sso.controller.ts:349`.

The ordinary LDAP login route applies `AuthRateLimitGuard`; the authenticated step-up route does not. With a valid synthetic session, 12 wrong-password step-up attempts against another LDAP account all returned 401, without 429. Ordinary login throttling was observed separately.

Impact: an authenticated attacker can repeatedly test directory credentials through step-up. Apply the same IP and target-account throttling to this route. Local evidence: `ldap-throttle.log`.

### SSO-02 - P1: OIDC always requests a nonstandard groups scope

Source: `apps/server/src/core/sso/sso.service.ts:507`.

The authorization scope is always `openid email profile groups`, including when group synchronization is disabled. A Keycloak client without the additional groups scope rejected the real login; the callback returned 401 while the configuration test returned 200. Adding that client scope at the IdP allowed login.

Impact: an otherwise valid OIDC configuration can pass testing but fail authentication. Use standard default scopes and explicitly configurable additional scopes. Local evidence: `matrix.log` and subsequent successful browser login.

### SSO-03 - P1: target-space authorization precedes group synchronization

Source: `apps/server/src/core/sso/sso.service.ts:756`.

Give a private space to a mapped SSO group, then authenticate a user who belongs to that group at the IdP but has no local membership yet. Login with `spaceSlug` returned 403 and created no session. Normal login synchronized the group; the same target-space login then succeeded.

Impact: users cannot enter a space directly on the login that should grant their access. Synchronize memberships before checking target access while preserving MFA policy enforcement. Local evidence: `space-target.log`.

### SSO-04 - P2: LDAP step-up does not refresh groups

Source: `apps/server/src/core/sso/sso.service.ts:720`.

After an LDAP login added a mapped group, removing the directory group attribute and completing LDAP step-up returned 200 but retained the membership. A full LDAP login removed it. OIDC and SAML step-up use a group-refresh path that LDAP step-up omits.

Impact: renewed SSO assurance can coexist with stale group-derived access. Share group synchronization and authorization notification behavior across protocols. Local evidence: `ldap-step-up.log`.

### SSO-05 - P2: an old configuration test can verify a newer configuration

Source: `apps/server/src/core/sso/sso.service.ts:1045`.

Using actual PostgreSQL and service methods, pause the network-check portion of a provider test, update its client configuration, then release the original test. The old test stamps the new configuration as verified because the update does not compare configuration versions.

Impact: the UI can report verification of settings that were never tested. This is a controlled-barrier reproduction, not a real network race measurement. `lastSuccessfulLoginAt` remained unset, so this did not establish an enforcement bypass. Add a version or `updatedAt` condition as used for successful-login recording. Local evidence: `db-probes.log`.

### SSO-06 - P2: rejected enforcement changes remain checked in the UI

Source: `apps/client/src/features/security/components/enforce-sso.tsx:56`.

Disable all providers and toggle enforcement in the browser. The server returns 400 and keeps enforcement false, but the switch remains checked. The component uses `defaultChecked` and only displays a notification after mutation failure.

Impact: the administrator sees a policy state that is not active. Control the switch from saved state, restore it on failure and prevent concurrent saves. Local evidence: `ui-admin.log` and `enforcement-rejection.png`.

## Additional risks and dependency review

- Endpoint policy validates resolved addresses but the protocol libraries resolve the hostname again for connection. DNS rebinding remains a static concern; no exploit was reproduced. See `sso-endpoint-policy.service.ts:67` and `sso.service.ts:1971`.
- Discovery/JWKS response size is checked after reading the response body, rather than during streaming (`sso.service.ts:2005`). Memory pressure was not load-tested.
- Installed `openid-client` 5.7.1 is outside the currently supported major version in the [maintainer security policy](https://github.com/panva/openid-client/security). This is a maintenance risk, not evidence of a reproduced vulnerability.
- Installed `node-saml` 5.1.0 includes the fix identified by [GHSA-4mxg-3p6v-xgq3](https://github.com/node-saml/node-saml/security/advisories/GHSA-4mxg-3p6v-xgq3).
- The production dependency audit reported six advisories (two high, four moderate) involving fast-uri, nodemailer, undici and ip-address. Their exploitability through SSO was not established; do not interpret the audit count as six SSO vulnerabilities.
