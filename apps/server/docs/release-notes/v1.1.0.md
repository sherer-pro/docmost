# Docmost v1.1.0 release notes

This document is the upgrade and rollback contract for installations moving
from `v1.0.0` to `v1.1.0`. Read it together with the
[PostgreSQL production migration runbook](../postgresql-production-migration.md)
and the generated API route inventory.

## Upgrade order

1. Back up PostgreSQL and file storage, record the currently deployed image
   digest, and rehearse the upgrade on a current production copy.
2. Rebase deployment configuration on `.env.production.example` (production)
   or the matching `.env.example` / `.env.compose.example` file. Do not reuse
   `APP_SECRET` as the collaboration credential.
3. Run `corepack pnpm check:release-version` and
   `corepack pnpm verify:release` against the candidate and production-like
   PostgreSQL, Redis, API, and collaboration processes.
4. Close ingress and run the production database `preflight` and `plan`. Use
   the logical volume migration workflow when preflight returns exit `20`.
5. Apply the ordered Kysely migrations once. Start and verify the dedicated
   collaboration process before starting the API process; the API does not
   host `/collab`.
6. Verify API and collaboration health, MCP initialize, PDF export, background
   work, and the security regression runbook before reopening ingress.
7. Ask users to sign in again. Access tokens issued before session binding was
   mandatory do not contain `sessionId` and are intentionally rejected.
8. Reopen ingress only after acceptance passes, then seal the rollback boundary
   with `corepack pnpm production:db -- accept --yes`.

The Docker release workflow accepts only the tag `v1.1.0` for manifests whose
version is `1.1.0`. Manual workflow runs use a non-release
`manual-<commit>` image tag.

## Configuration and secrets

The upgrade introduces or tightens several deployment contracts. Diff the
complete example file for the selected deployment mode; the important groups
are:

- dedicated collaboration: `COLLAB_URL`, `COLLAB_INTERNAL_URL`,
  `COLLAB_INTERNAL_SECRET` or `COLLAB_INTERNAL_SECRET_FILE`, and `COLLAB_PORT`;
- externalized production secrets: `APP_SECRET_FILE`, `DATABASE_URL_FILE`,
  `REDIS_URL_FILE`, and `POSTGRES_PASSWORD_FILE`;
- proxy and authentication boundaries: `TRUSTED_PROXIES` and production
  `AUTH_RATE_LIMIT_STORAGE=redis`;
- outbound allowlists and kill switches: `SSO_ALLOWED_ENDPOINTS`,
  `AI_PROVIDER_ALLOWED_ORIGINS`, `AI_RETRIEVAL_ALLOWED_ORIGINS`,
  `AI_EXTERNAL_MCP_ENABLED`, `AI_MCP_ALLOWED_ORIGINS`,
  `RAG_SYNC_ENABLED`, and `RAG_SYNC_ALLOWED_ORIGINS`;
- production/runtime controls: `DATABASE_MIGRATION_MODE`, `DRAWIO_URL`,
  `PDF_CHROMIUM_EXECUTABLE_PATH`, and the documented RAG/MCP concurrency and
  timeout limits.

Keep optional external integrations disabled until their exact origins and
credentials have been approved. RAG Sync targets configured before this
release remain unverified and must pass **Test** before **Enable**.

## API and session compatibility

- The read-like POST and legacy command aliases removed in August 2026 are not
  restored. Clients must use the canonical routes in
  `api-route-inventory.generated.md` and the
  [alias removal note](./api-alias-removal-2026-08.md).
- Only the two persisted-content compatibility routes
  `GET /api/files/:fileId/:fileName` and
  `GET /api/files/public/:fileId/:fileName` remain.
- User JWTs and collaboration tokens must be bound to an active `sessionId`.
  Older access tokens require a new sign-in.
- `POST /api/version`, inbound MCP `serverInfo.version`, and outbound MCP
  `clientInfo.version` report `1.1.0`.

## Rollback boundary

Do not use `migration:down` as an operational rollback. Several migrations
remove or normalize legacy state, and several down paths destroy policy,
credential, snapshot, outbox, or verification data.

Before ingress admits writes, rollback may select the previous image and
database volume with `corepack pnpm production:db -- rollback --yes`. After
`production:db -- accept --yes`, automatic rollback is forbidden because the
old volume no longer contains post-cutover writes. Recovery then requires a new
planned migration or a DBA-approved point-in-time restore.

Prefer documented runtime kill switches for optional AI, external MCP, page
template, and RAG Sync behavior so the migrated data remains intact.

## Release evidence boundary

Local sign-off requires the full release gate, the production-image smoke, the
pinned Open WebUI compatibility suite, and the manual security runbook. A local
pass does not prove GitHub-hosted execution or live Typesense, SSO/LDAP, SMTP,
Web Push, or external MCP interoperability; those integrations require
contract, negative, and fail-closed coverage for the candidate and remain
post-RC live checks when endpoints are unavailable.
