# Docmost v1.2.5 release notes

`v1.2.5` is a reliability release for API/collaboration self-healing, bounded
search projection, and large Docmost archive exports. It supersedes `v1.2.4`.

## Runtime reliability

- The production image now starts a first-party Node.js supervisor as PID 1.
  API and collaboration run as independent children and recover independently
  through Compose `restart: unless-stopped`.
- The supervisor probes `/api/health/live` every five seconds with a two-second
  timeout and 60-second startup grace. Three consecutive failures cause
  `SIGTERM`, a five-second forced-kill boundary for an unresponsive child, and a
  non-zero container exit. External shutdown signals retain the application's
  ordinary graceful-shutdown window.
- `/api/health` remains the PostgreSQL/Redis readiness endpoint;
  `/api/health/live` remains process liveness. No public route was added.
- API and collaboration always sample V8 memory every 30 seconds and emit only
  privacy-safe warning, critical, reminder, and recovery events. Heap dumps and
  user/request data are never recorded. Detailed route diagnostics remain off
  by default.

## Bounded search and exports

- Database and Typesense projection use cursor pagination and process at most
  100 database/reconciliation records at once.
- Typesense imports are sequential and limited to 100 documents and 4 MiB per
  request; one larger document is isolated in its own request. Attachment
  projection and stale-document deletion no longer create unbounded concurrent
  work. A single shared pair of keep-alive agents replaces per-import agents and
  is explicitly destroyed during shutdown.
- Docmost archive export streams ZIP output and bounds internal attachment work,
  avoiding full-archive buffering for large exports.

The Typesense collection schemas and aliases are unchanged. A reindex is not
required solely for this upgrade.

## Verification and upgrade

CI now blocks publication unless the production-built search projection passes
an eight-cycle heap slope/plateau gate and the immutable production image passes
authenticated Socket.IO churn plus API-child `SIGSTOP` recovery. The recovery
test also proves that collaboration, PostgreSQL, and Redis did not restart.
Do not repeat this fault injection in production.

There are no new database migrations in `v1.2.5`. Operators must still use the
normal coordinated backup, disposable restore rehearsal, production preflight,
plan, maintenance fence, and `production:db migrate --yes` workflow. Treat the
migration step as a required no-op schema verification. Before `accept`, verify
both supervisor/child process trees, internal and external readiness, sign-in,
Socket.IO/collaboration, Typesense, RSS/CPU, and the absence of heap-critical
events, then observe the deployment for 30 minutes.

Rollback before `accept` uses the documented `production:db rollback --yes`
path and the previous immutable application digest. No schema or search-schema
rollback is required. After `accept`, use only the documented forward-recovery
procedure.

The Docker release workflow accepts only tag `v1.2.5` for manifests whose
version is `1.2.5`. Deploy only the registry digest whose OCI
`org.opencontainers.image.version` is `1.2.5` and whose OCI revision equals the
tagged commit.
