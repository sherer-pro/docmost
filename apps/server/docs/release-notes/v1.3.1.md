# Docmost v1.3.1 release notes

`v1.3.1` replaces the space settings modal with dedicated administration pages,
adds a searchable management list, and moves template enablement entirely into
space settings.

## Space administration

- `/settings/spaces` searches names, descriptions, and addresses before stable
  20-item cursor pagination. Active, archived, and all-space views retain their
  filters and list position. Responsive cards expose member counts, access
  requirements, and template, dictionary, and AI states according to privileges.
- Eight settings sections provide explicit Save and Cancel actions, independent
  group-template permission forms, retained drafts after errors or background
  refreshes, and unsaved-change warnings for links and browser navigation.
  Existing entry points and AI return links use the new routes.
- Returning to a document preserves the control already selected by the user;
  delayed title autofocus no longer steals input from the document editor.
  Document search also releases destroyed editors and follows their replacement
  during navigation, preventing errors when returning from settings.
- Workspace settings explain identity and history-retention scope. The workspace
  template switch is removed. All 12 locales and AI administrator guide version
  23 describe the new behavior.

`GET /api/spaces/administration` is an additive, permission-filtered summary
contract. Pending MFA/SSO responses contain only minimal identity and sign-in
requirements. AI summaries describe configuration, not provider availability.
`PATCH /api/spaces/:spaceId` commits settings and related public-link deletion
atomically; authorization and RAG events follow successful commit.

## Template migration and compatibility

Migration `20260919T180000-space-owned-template-policy` folds the previous
workspace gate into every stored space policy: new local enablement equals old
local enablement AND old workspace enablement. Missing workspace policy means
disabled. The deployment flag `PAGE_TEMPLATES_ENABLED` is excluded from the
data migration and remains an active runtime switch. New spaces remain disabled.
Action/group permissions, template content, and linked pages are preserved.

Legacy reads retain `workspaceEnabled: true`; the workspace policy GET exposes
its deprecation. The former workspace policy PATCH returns HTTP 410 with code
`page_template_workspace_policy_retired`. Integrations must manage space policies.
Space and group policy writes retain `expectedRevision` conflict checks.

Original policies and context are preserved in
`page_template_workspace_gate_backup` and `page_template_workspace_gate_context`.
The down migration restores them only when no policy was subsequently changed,
added, or removed. Do not force rollback or delete these service tables.
See [space administration](../../../../docs/SPACE_ADMINISTRATION.md) for the
complete settings and compatibility contracts.

## Dependency security updates

The production dependency audit identified new high-severity advisories since
the previous release. This release pins `@tiptap/core` and its required
`@tiptap/pm` peer to `3.30.5`, `@xmldom/xmldom` to `0.8.15`, and Nodemailer to
`9.1.1`. Existing Tiptap extensions retain their compatible versions and the
BubbleMenu lifecycle patch. ProseMirror model, state, transform, and view versions
are aligned across the editor and collaboration packages. The fixes cover
[Markdown attribute parsing](https://github.com/advisories/GHSA-j95f-988m-3j2f),
[XML parsing](https://github.com/advisories/GHSA-93r5-fhx6-vmg9), and
[mail address parsing](https://github.com/advisories/GHSA-2x7j-588g-ccc2).

## Upgrade, acceptance, and rollback

Deploy the immutable `shererpro/docmost:1.3.1` registry digest with OCI version
`1.3.1` and a revision matching the release tag commit. Include production,
canonical Typesense when enabled, and all required host overlays. Preserve
existing credentials, allowlists, infrastructure images, limits, and volumes.
Read the release notes for every version crossed during the upgrade.

Create and verify a coordinated PostgreSQL/file-storage backup and an off-host
copy. Rehearse restoration, upgrade, and rollback against a current isolated
production copy with real mail and external synchronization disabled. Run the
release verification suite and use `production:db` preflight, plan, and migrate.
Keep ingress closed until acceptance is complete.

Verify sign-in, page save/reload, attachments, two-session collaboration,
Draw.io, and page/attachment/dictionary search. In a synthetic space verify the
administrative list, direct section routes, Save/Cancel, navigation warnings,
AI return links, and template policy preservation. Check that legacy writes
return 410 and that authorization and MFA/SSO restrictions remain effective.
Observe service health, restarts, OOM, critical errors, and database collation
warnings for 30 minutes before accepting the deployment.

Before admitting public writes, recover through `production:db rollback --yes`
using the recorded previous image and database volume. On successful acceptance,
run `production:db accept --yes` and retain the previous image, volume, and
verified backups for at least 14 days. After acceptance, automatic volume rollback
is forbidden because it would discard newly admitted writes.
