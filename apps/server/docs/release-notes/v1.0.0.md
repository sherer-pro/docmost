# Docmost v1.0.0 release notes

This document records the upgrade and rollback contract for installations
moving from `v0.34.1` to `v1.0.0`. It was reconstructed from the tagged
repository range `v0.34.1..v1.0.0`; it does not claim retrospective production
acceptance evidence. Installations upgrading beyond this release must follow
every later release note in order, starting with the
[v1.1.0 upgrade notes](./v1.1.0.md).

## Release scope

`v1.0.0` is the first stable release of this fork. It removes the separate
Enterprise Edition application layer and moves the maintained SSO, MFA,
comments, advanced search, sharing controls, and related administration
capabilities into the AGPL core.

The release also establishes the fork's first integrated AI platform:

- private per-space AI conversations, editor actions, files, source snapshots,
  reasoning, retries, cancellation, quotas, and recovery;
- access-aware query-time retrieval, the external RAG synchronization API, and
  optional Open WebUI retrieval and synchronization;
- bounded Agent mode with explicit approval for page changes and a stateless,
  read-only inbound MCP endpoint;
- separate space-scoped `rag` and `mcp` API-key types with live membership and
  page-access revalidation;
- PostgreSQL and optional Typesense search for pages and extracted attachment
  content, with bounded PDF and DOCX processing;
- core OIDC, SAML, and LDAP provider management with endpoint allowlisting,
  provider verification, and explicit group mappings.

The tagged release also includes the fork's Notion-style databases, extended
document properties, dictionary and tag workflows, editor extensions,
import/export hardening, notifications, page access rules, and PWA changes.
The current feature overview in the root `README.md` may include capabilities
added after `v1.0.0`; the tag is the source of truth for this release.

## Upgrade order

1. Create and verify backups of PostgreSQL and file storage. Record the exact
   `v0.34.1` application image and database runtime, and rehearse the upgrade on
   a current production copy.
2. Follow the current
   [PostgreSQL production migration runbook](../postgresql-production-migration.md).
   Do not attach an existing Alpine/musl PostgreSQL volume directly to the
   Debian/glibc PostgreSQL 18 runtime used by `v1.0.0`.
3. Diff the `v1.0.0` `.env.example` and Compose files against the deployment.
   Approve exact outbound provider, retrieval, and SSO origins before enabling
   those integrations; keep optional integrations disabled otherwise.
4. Enter maintenance mode, stop writes, and apply the 16 ordered Kysely
   migrations once. Do not run individual migration files manually.
5. Start the base API, PostgreSQL, and Redis stack and verify authentication,
   page access, search, imports/exports, attachments, and background work before
   enabling Typesense, AI providers, SSO, RAG, MCP, or the optional Open WebUI
   synchronization worker.
6. Reopen ingress only after acceptance succeeds. Preserve the previous image,
   database backup or volume, file-storage backup, and deployment configuration
   until the rollback boundary is explicitly accepted.

## Data and compatibility boundaries

- Existing API keys are classified as `rag`; create a distinct `mcp` key for
  the inbound MCP endpoint.
- The core SSO migration resets existing `enforce_sso` values to `false`.
  Configure the endpoint allowlist, verify a provider, complete a real login,
  and only then explicitly re-enable enforcement.
- Retired Confluence and DOCX import tasks, legacy workspace AI-search settings,
  and `page_embeddings` are removed. The migration deliberately has no data-
  restoring `down` path.
- Obsolete Enterprise Edition license and billing schema is removed. Do not
  plan a rollback that depends on recreating that state through migrations.
- Duplicate active page shares are cleaned up before database uniqueness is
  enforced. Validate public links and workspace/space sharing policy during
  acceptance.
- Attachment content indexing becomes explicit and recoverable. If Typesense
  is enabled, rebuild and verify the projection rather than treating it as
  authoritative data.

## Configuration boundaries

Review the complete examples from the tag. The most important new or tightened
groups are:

- outbound trust: `AI_PROVIDER_ALLOWED_ORIGINS`,
  `AI_RETRIEVAL_ALLOWED_ORIGINS`, and `SSO_ALLOWED_ENDPOINTS`;
- admission control: `RAG_API_RATE_LIMIT_PER_MINUTE`,
  `RAG_API_MAX_CONCURRENT`, `RAG_API_BULK_MAX_CONCURRENT`,
  `MCP_RATE_LIMIT_PER_MINUTE`, and `MCP_MAX_CONCURRENT`;
- proxy and authentication: `TRUSTED_PROXIES` and production
  `AUTH_RATE_LIMIT_STORAGE=redis`;
- search and rendering: `SEARCH_DRIVER`, `TYPESENSE_URL`,
  `TYPESENSE_API_KEY`, `PDF_CHROMIUM_EXECUTABLE_PATH`, and `DRAWIO_URL`.

Provider, retrieval, SSO, RAG, MCP, Typesense, mail, Web Push, and object-storage
credentials are deployment secrets. Do not place them in release notes,
versioned Compose overrides, logs, or acceptance artifacts.

## Rollback boundary

Do not use `migration:down` as an operational rollback. Several `v1.0.0`
migrations remove legacy data or drop newly persisted conversations, source
snapshots, credentials, approval history, reasoning, content policy, and index
state on `down`.

Before ingress admits writes, rollback means restoring the previous application
image together with the preserved `v0.34.1` database and file storage. After
new writes are accepted on the migrated database, the old volume is stale;
recovery requires a planned forward fix or a DBA-approved point-in-time restore.

Use feature configuration to disable optional AI, SSO, RAG, MCP, Typesense, and
Open WebUI integrations without destroying migrated data.
