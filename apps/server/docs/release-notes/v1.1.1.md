# Docmost v1.1.1 release notes

This document is the upgrade and rollback contract for installations moving
from `v1.1.0` to `v1.1.1`. Installations still on `v1.0.0` must also follow the
[v1.1.0 upgrade notes](./v1.1.0.md) and the
[PostgreSQL production migration runbook](../postgresql-production-migration.md).

## Upgrade order

1. Create and verify a coordinated PostgreSQL and storage backup. Record the
   current application image digest, PostgreSQL image, and volume names.
2. Run `corepack pnpm check:release-version` and
   `corepack pnpm verify:release` against the exact candidate image and the
   documented production-like PostgreSQL, Redis, API, and collaboration stack.
3. Validate both normal and maintenance ingress configurations. Enter
   maintenance before any PostgreSQL volume migration or schema operation.
4. Provision the dedicated collaboration process before the API. Both must use
   the same application image and independent application and collaboration
   secrets; the API never hosts `/collab`.
5. Apply migrations once, verify `/api/health` on the collaboration and API
   processes, then reopen ingress.
6. Exercise coordinated backup verification and a disposable restore before
   sealing the rollback boundary with `production:db -- accept --yes`.

The Docker release workflow accepts only the tag `v1.1.1` for manifests whose
version is `1.1.1`. The production image must carry the release commit as the
OCI revision label and is deployed by registry digest.

## Database compatibility

There are no new Kysely migrations between `v1.1.0` and `v1.1.1`. The supported
production PostgreSQL runtime remains the pinned Debian/glibc PostgreSQL 18
image. An installation upgrading directly from `v1.0.0` still has to apply all
migrations listed in the v1.1.0 release notes.

Do not attach a PostgreSQL 16 Alpine volume to PostgreSQL 18. Use the logical
volume migration workflow, keep the old volume intact until acceptance, and
roll back to the old image and volume together if pre-ingress validation fails.

## Runtime fixes

- The API and collaboration processes have an explicit Compose routing
  contract, preventing the API from accidentally becoming the `/collab`
  endpoint.
- Page-template operations recover predictably from collaboration outages and
  their live collaboration lifecycle is covered by dedicated tests.
- Table-of-contents navigation no longer races editor scrolling.
- Markdown and PDF export preserve multiline Mermaid labels, and synced blocks
  are covered in Markdown export tests.
- Unreachable attachment helpers were removed without restoring retired public
  routes.

## Backup and operational changes

The release includes coordinated Compose backup tooling and the canonical
[backup and restore runbook](../../../../docs/BACKUP_AND_RESTORE.md). A current
archive contains only `manifest.json`, `postgres.dump`, and `storage.tar.gz`;
secrets are escrowed separately and Redis is recreated empty.

Use `pnpm backup -- create`, `pnpm backup -- verify`, and the destructive
`pnpm backup -- restore --replace --yes` only as described in the runbook. A
successful archive checksum is not restore evidence: acceptance requires an
isolated PostgreSQL restore, a storage inventory comparison, and an application
health check on the restored copy.

## Rollback boundary

Before ingress admits writes, rollback may select the previous application
image and the untouched PostgreSQL volume with
`corepack pnpm production:db -- rollback --yes`. Do not use `migration:down` as
an operational rollback.

An installation coming directly from `v1.0.0` may have a previous image that
lacks the dedicated collaboration and preflight entry points. Such an upgrade
must configure the rehearsed `DOCMOST_ROLLBACK_HOOK`; automatic rollback then
restores the preserved legacy Compose stack and previous ingress instead of
trying to force that image through the new topology.

If that external hook is interrupted, the state remains `rollback_preflight`
and ingress must remain in maintenance mode. Fix the hook and repeat the same
`production:db -- rollback --yes` command: it resumes the rollback, checks the
previous database preflight class, and only then records `rolled_back`. Do not
edit the deployment state file by hand.

After a completed rollback, `production:db -- preflight` and
`production:db -- plan` inspect the preserved source database with the
configured target image. The recorded legacy image remains rollback evidence;
it is not asked to provide database tooling that did not exist in that release.

After `production:db -- accept --yes`, the old volume no longer contains new
writes and automatic rollback is forbidden. Recovery then requires a planned
forward fix or a DBA-approved point-in-time restore.

## Release evidence boundary

`verify:full`, a successful image build, and local Compose smoke prove only the
tested local candidate. They do not prove GitHub-hosted execution, Docker Hub
publication, live SMTP, SSO/LDAP, Web Push, Typesense, or external AI/MCP
providers. Record those live checks separately when the corresponding services
are available.
