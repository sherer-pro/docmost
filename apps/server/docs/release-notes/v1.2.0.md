# Docmost v1.2.0 release notes

This document is the upgrade and rollback contract for installations moving
from `v1.1.1` to `v1.2.0`. Installations still on `v1.1.0` or `v1.0.0` must also
follow the [v1.1.1 upgrade notes](./v1.1.1.md), the
[v1.1.0 upgrade notes](./v1.1.0.md), and the
[PostgreSQL production migration runbook](../postgresql-production-migration.md).

## Upgrade order

1. Create and verify a coordinated PostgreSQL and storage backup. Record the
   current application image digest, PostgreSQL image, and volume names.
2. Run `corepack pnpm check:release-version` and
   `corepack pnpm verify:release` against the exact candidate image and the
   documented production-like PostgreSQL, Redis, API, and collaboration stack.
3. Validate both normal and maintenance ingress configurations. Enter
   maintenance before any PostgreSQL volume migration or schema operation. This
   release contains a table-wide backfill, so plan the maintenance window with
   the `pages` row count in mind.
4. Provision the dedicated collaboration process before the API. Both must use
   the same application image and independent application and collaboration
   secrets; the API never hosts `/collab`.
5. Apply migrations once, verify `/api/health` on the collaboration and API
   processes, then reopen ingress.
6. Exercise coordinated backup verification and a disposable restore before
   sealing the rollback boundary with `production:db -- accept --yes`.

The Docker release workflow accepts only the tag `v1.2.0` for manifests whose
version is `1.2.0`. The production image must carry the release commit as the
OCI revision label and is deployed by registry digest.

## Database compatibility

This release adds one Kysely migration,
`20260816T120000-page-tag-values.ts`, which backs indexed tag search:

- the immutable `extract_page_tag_values(jsonb)` function that collects
  normalized inline tag values from page content;
- the `pages.tag_values text[]` column with an empty-array default;
- the `pages_tag_values_update` trigger, which recomputes `tag_values` on every
  insert and on every `content` update;
- a one-time backfill that rewrites `tag_values` for every existing page;
- the partial GIN index `pages_tag_values_search_idx`, restricted to live
  non-template pages.

The backfill updates all rows of `pages` in a single statement. On a large
workspace it needs the maintenance window, temporary WAL and table bloat
headroom, and a `VACUUM`/autovacuum pass afterwards. The migration `down`
removes the index, trigger, both functions, and the column; use it only for
pre-ingress recovery, never as an operational rollback.

The supported production PostgreSQL runtime remains the pinned Debian/glibc
PostgreSQL 18 image. Do not attach a PostgreSQL 16 Alpine volume to
PostgreSQL 18. Use the logical volume migration workflow, keep the old volume
intact until acceptance, and roll back to the old image and volume together if
pre-ingress validation fails.

## New functionality

- Indexed page tag search: a dedicated search API over the new `tag_values`
  column plus the tag discovery UI. Tags are matched in normalized lowercase
  form, and only live non-template pages are indexed.
- The AI administrator guide at `/settings/ai/guide` was redesigned. Its
  structured scenarios, anchors, locale manifest, and contract version stay the
  canonical projection of [`docs/AI_ASSISTANT_AND_RAG.md`](../../../../docs/AI_ASSISTANT_AND_RAG.md).

## Runtime fixes

- Pressing Enter now closes fenced code blocks in the editor instead of
  extending them.
- The AI page-templates button icon matches the rest of the editor toolbar.

## Deployment and operations tooling

The production database migration and rollback tooling
(`corepack pnpm production:db -- ...`) was hardened in this release:

- legacy rollback paths are version-safe and no longer ask a previous image for
  database tooling it never shipped;
- the `pnpm` argument separator is accepted in every documented invocation;
- root-owned storage is archived without losing ownership metadata;
- a failed retry restarts from the target image;
- migration failure evidence is preserved instead of being overwritten;
- the stable PostgreSQL inventory comparison no longer reports spurious drift;
- an interrupted rollback resumes from the recorded state;
- preflight inspects the preserved source database after a completed rollback.

The [PostgreSQL production migration runbook](../postgresql-production-migration.md)
and the [backup and restore runbook](../../../../docs/BACKUP_AND_RESTORE.md)
were updated in the same change, including the closed forensic restore drills.

## CI and release gate changes

- `ci.yml` now also runs on `push` to `main`, so a broken `main` is detected
  between releases instead of at release time. Superseded `push` and
  `pull_request` runs are cancelled; release gate runs called from `docker.yml`
  are not.
- The `production-smoke` collaboration container runs with
  `PAGE_TEMPLATES_ENABLED=true`, matching both API runtimes, and the release
  gate contract enforces it.
- The shared browser-acceptance Python requirements pin `markdown-it-py`, so
  export artifact verification no longer depends on a Node package that is only
  a transitive dependency.
- The scheduled Open WebUI compatibility workflow installs workspace
  dependencies with pinned pnpm before running the audit, and preserves the
  sanitized failure log captured while its containers are still alive.

## Rollback boundary

Before ingress admits writes, rollback may select the previous application
image and the untouched PostgreSQL volume with
`corepack pnpm production:db -- rollback --yes`. Do not use `migration:down` as
an operational rollback.

An installation coming from `v1.0.0` may have a previous image that lacks the
dedicated collaboration and preflight entry points. Such an upgrade must
configure the rehearsed `DOCMOST_ROLLBACK_HOOK`; automatic rollback then
restores the preserved legacy Compose stack and previous ingress instead of
trying to force that image through the new topology.

If that external hook is interrupted, the state remains `rollback_preflight`
and ingress must remain in maintenance mode. Fix the hook and repeat the same
`production:db -- rollback --yes` command: it resumes the rollback, checks the
previous database preflight class, and only then records `rolled_back`. Do not
edit the deployment state file by hand.

After `production:db -- accept --yes`, the old volume no longer contains new
writes and automatic rollback is forbidden. Recovery then requires a planned
forward fix or a DBA-approved point-in-time restore.

## Release evidence boundary

`verify:full`, a successful image build, and local Compose smoke prove only the
tested local candidate. They do not prove GitHub-hosted execution, Docker Hub
publication, live SMTP, SSO/LDAP, Web Push, Typesense, or external AI/MCP
providers. Record those live checks separately when the corresponding services
are available.
