# Docmost v1.2.1 release notes

This document is the upgrade and rollback contract for installations moving
from `v1.2.0` to `v1.2.1`. Installations on an earlier release must also follow
every intervening release note and the
[PostgreSQL production migration runbook](../postgresql-production-migration.md).

## Upgrade order

1. Create and verify a coordinated PostgreSQL and file-storage backup. Record
   the current application image digest, PostgreSQL image, volume names, and
   deployment state before changing the candidate image.
2. Keep ingress open and run the read-only checks in order:
   `corepack pnpm production:db -- preflight --json`, then
   `corepack pnpm production:db -- plan --json`. Resolve every blocked result;
   do not weaken the capacity thresholds.
3. Pin the `v1.2.1` image by immutable digest, confirm the previous image is
   still available, and enter the rehearsed maintenance window with the
   maintenance hooks configured.
4. Run `corepack pnpm production:db -- migrate --yes --json`. The supported
   operator keeps ingress closed while it creates and verifies the backup,
   applies the migrations, starts PostgreSQL, collaboration, and API in order,
   and leaves the deployment state in `acceptance`.
5. While ingress is still closed, run application, collaboration, search, ACL,
   storage, and database acceptance. Queue the mandatory reindex described
   below and wait for it to complete before judging search readiness.
6. If acceptance fails, run the pre-ingress recovery command
   `corepack pnpm production:db -- rollback --yes --json`. If acceptance passes,
   run `corepack pnpm production:db -- accept --yes --json` to reopen ingress
   and seal the rollback boundary.

The Docker release workflow accepts only the tag `v1.2.1` for manifests whose
version is `1.2.1`. The production image must carry the release commit as the
OCI revision label and must be deployed by registry digest.

## Database migrations and capacity

This release adds three ordered Kysely migrations:

- `20260820T120000-move-tag-settings-to-spaces.ts` copies the workspace tag
  configuration into every existing space and removes the workspace-level
  copy. This is a data rewrite across the space settings rows. Its `down` path
  deliberately refuses to collapse divergent per-space settings.
- `20260820T130000-knowledge-projection-dictionary-search.ts` extends the
  `ai_message_sources_source_type_check` constraint with `dictionary_term`.
  It performs no search-index build. Its `down` path deletes dictionary source
  rows because the previous constraint cannot represent them.
- `20260820T140000-search-dictionary-database-projection.ts` creates the three
  dictionary trigram indexes using the same
  `LOWER(f_unaccent(...))` expressions as the query path, adds the database-row
  search projection columns and trigger to `pages`, rewrites every existing
  `pages` row to populate `database_search_tsv`, and creates the partial GIN
  index `idx_pages_database_search_tsv`.

The `140000` migration performs ordinary index builds and a full-table update;
the dictionary indexes also scan their source tables. Schedule a maintenance
window sized from production row counts. Provide headroom for the new indexes,
the rewritten table, temporary files, WAL, replication lag, and a subsequent
`VACUUM` or autovacuum pass. The read-only `plan` result and a rehearsal on a
current production copy are the capacity evidence; a successful local build is
not a substitute.

## Mandatory post-upgrade reindex

After the schema migration, existing database-row projections and Typesense
collections are not considered release-ready until a full reindex completes:

```bash
corepack pnpm --filter ./apps/server search:reindex -- \
  --workspace=all \
  --entities=pages,attachments,dictionary
```

When only the production image is available, run the built CLI in the
application container as documented in [`docs/SEARCH.md`](../../../../docs/SEARCH.md).
Including `pages` rebuilds derived database-row projections. The full run also
builds and validates the new Typesense page, attachment, and dictionary
generations before their aliases switch. PostgreSQL remains authoritative;
monitor the queue, alias-switch events, reconciliation counts, and
representative queries with both search drivers.

## New functionality and public contracts

- Search now covers dictionary terms, aliases, forms, definitions, and selected
  database cell values. Spotlight `All` mode exposes document, attachment, and
  dictionary sections, while database results carry matched-property context.
- RAG export and built-in RAG Sync use a unified knowledge projection for
  pages, databases, database rows, attachments, and dictionary terms. AI
  retrieval and tools expose knowledge Markdown, supported custom fields, and
  database-property details.
- Inline tag configuration is space-scoped and travels with portable space
  settings instead of remaining workspace-global.

The release preparation itself adds no wire contract. It documents contracts
already implemented after `v1.2.0`:

- `GET /dictionary-terms/:termId`, `GET /pages/references`, and
  `POST /search/dictionary`;
- `GET /rag/dictionary/terms`, `GET /rag/dictionary/terms/:termId`,
  `GET /rag/dictionary/updates`, and `GET /rag/dictionary/deleted`;
- `dictionary_term` in the AI and RAG source unions, plus
  `projectionVersion: 1` in knowledge projection scope and the associated
  knowledge/custom-field/database-property data;
- the terminal RAG Sync error `rag_sync_target_mismatch` when persisted source
  provenance no longer matches the configured target;
- tag settings in portable space settings and space import/export.

These route paths are mounted below the normal Docmost `/api` prefix. Existing
authentication, workspace/space scope, API-key policy, page ACL, and CSRF
requirements remain in force for the corresponding route class.

## Mandatory release documentation acceptance

Release preparation must run `corepack pnpm check:fork-docs` and the complete
`corepack pnpm verify:release` contract. The fork-documentation gate blocks on
drift between the English fork section in `README.md` and
`FORK_SPECIFIC_ENHANCEMENTS_RU.md`: both documents must keep the same 16
numbered capability sections, matching capability-list cardinality, paired
images, stable administrator-guide anchors, and the critical semantic concepts
recorded in `docs/fork-specific-enhancements-contract.json`.

The production-like `test:ai:e2e` stage opens `/settings/ai/guide` as its own
administrator-only AI settings tab in both Russian and English, traverses all
eight stable panels, verifies `projectionVersion: 1`, the `dictionary_term`
knowledge and RAG Sync paths, and `rag_sync_target_mismatch` guidance, and
records browser evidence. Static
`check:ai-docs` validation additionally rejects moving the route outside the
workspace-administrator boundary, folding the guide into another tab, or
removing the bilingual browser scenario.

## Host-specific deployment landmarks

The current `AllDocker` host instructions remain the site-specific overlay for
this generic release contract. On that host:

- run the repository `compose.production.yml` together with the mandatory
  `compose.limits.yml` from the current Docmost release directory (documented
  today under `/opt/docmost-v1.1.1`); do not overwrite the preserved legacy
  `/opt/docmost` rollback directory;
- keep deployment configuration and secrets in
  `/etc/docmost/docmost.env` with the documented root-only permissions;
- keep the non-secret migration state in
  `/var/lib/docmost/deployment/postgres.env`; never edit it by hand while the
  Compose stack is running;
- keep the maintenance enter/exit hooks executable and idempotent. They must
  stop new HTTP writes and WebSocket upgrades before migration and restore
  routing only after both application processes are healthy.

The vault instructions are operational input, not release artifacts. Copy the
candidate files to a versioned release directory and verify the effective
base-plus-limits Compose configuration before the maintenance window.

## Rollback boundary

Before ingress admits writes, rollback may select the previous image and the
untouched PostgreSQL volume with
`corepack pnpm production:db -- rollback --yes --json`. Do not use
`migration:down` as an operational rollback: the `120000` and `130000` down
paths are intentionally destructive when the new data can no longer be
represented.

After `corepack pnpm production:db -- accept --yes --json`, automatic rollback
is forbidden because the preserved old volume no longer contains accepted
writes. Recovery then requires a planned forward fix or a DBA-approved logical
or point-in-time restore.

## Release evidence boundary

Local `verify:full`, `verify:release`, image inspection, and disposable upgrade
acceptance prove only the exact local candidate. They do not prove hosted CI,
staging load and capacity, Docker Hub publication, production deployment, live
SMTP/SSO/Web Push/Typesense/AI/Open WebUI integrations, or a real production
rollback. Record those checks separately when the corresponding environments
and services are available.
