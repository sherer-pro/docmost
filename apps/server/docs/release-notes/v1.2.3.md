# Docmost v1.2.3 release notes

This document is the upgrade and rollback contract for installations moving
from `v1.2.2` to `v1.2.3`. Installations on an earlier release must also follow
every intervening release note, including the
[v1.2.2 upgrade notes](./v1.2.2.md) and the mandatory migrations and search
reindex in the [v1.2.1 upgrade notes](./v1.2.1.md), together with the
[production deployment guide](../../../../docs/DEPLOYMENT.md).

## Upgrade order

1. Create and verify a coordinated PostgreSQL and file-storage backup. Record
   the current application image digest, PostgreSQL image, volume names, and
   deployment state.
2. Run the read-only production database `preflight` and `plan` commands from
   the exact candidate checkout. Resolve blocked results before maintenance.
3. Pin the `v1.2.3` image by immutable digest and confirm the previous image is
   still available. Enter the rehearsed maintenance window before changing the
   application processes.
4. Before starting the migration operator, run the candidate's read-only
   [`page-embed:prepare-removal` plan](../page-embed-removal-runbook.md) against
   the pre-T040 schema. Keep API, collaboration, workers, and ingress stopped,
   then always run the bounded, resumable apply path with both maintenance and
   verified-backup acknowledgements. Apply is required even when the plan is
   clean because it records the per-page hash ledger verified by T040. Supply
   surface policy flags only when they appear in the plan's
   `requiredPolicies`, then rerun the read-only plan before migration.
   A failed retired operation with staged content or a non-empty attachment
   mapping also blocks removal because that row may be the only cleanup ledger.
   Reconcile its referenced storage with the previous compatible release and a
   verified backup; do not bypass the precondition by deleting the row.
5. Run the production migration operator. It applies the ordered
   `20260822T010000` through `20260822T050000` migrations described below.
   T040 verifies the cleanup ledgers and remains fail-closed if any covered
   content, reference, operation, or attachment-clone state is unresolved.
6. Remove the retired `MAX_PAGE_EMBED_DEPTH` key from deployment-local
   environment files. Whole-page embeds no longer have a runtime depth policy,
   and the checked-in environment contract intentionally excludes this key.
7. Start PostgreSQL, collaboration, and API in the documented order. While
   ingress remains closed, verify application health, collaboration, search,
   page templates, storage, and any enabled RAG Sync binding.
8. If acceptance fails, run the documented pre-ingress rollback. If it passes,
   accept the deployment to reopen ingress and seal the rollback boundary.

The Docker release workflow accepts only the tag `v1.2.3` for manifests whose
version is `1.2.3`. The production image must carry the release commit as the
OCI revision label and must be deployed by registry digest.

## Database and search compatibility

The following Kysely migrations are new and must run in this exact order:

1. `20260822T010000-durable-deletions-and-imports` adds durable attachment
   cleanup/import admission artifacts and outbox work, including recovery for
   confirmed Docmost imports. Its down path is intentionally blocked while
   cleanup, active imports, or uncompensated storage artifacts remain.
2. `20260822T020000-history-retention-and-operational-indexes` adds stable page
   history batch identity, configurable workspace retention, page-history and
   attachment indexes, and terminal outbox indexes. Its down path drops the
   new retention setting and batch identity and is not a data-preserving
   operational rollback.
3. `20260822T030000-page-duplicate-idempotency` admits the modern
   `page_duplicate` operation kind. Its down path deletes those operation rows.
4. `20260822T040000-remove-legacy-page-embeds` first proves that page content,
   Yjs payloads, history, synced-block/template data, rich content, whole-page
   reference rows, and pending legacy operations no longer retain `pageEmbed`.
   Failed retired operations that retain staged content or attachment mappings
   also block the migration until their possible orphaned storage is reconciled.
   It then removes terminal retired operation rows and the legacy graph,
   reference, and migration-error schema while preserving exactly `snapshot`,
   `page_duplicate`, `template_sync`, and `template_detach` operation kinds.
   The remaining block-reference schema again enforces
   `source_page_id -> pages(id) ON DELETE CASCADE`.
   Its down path can recreate empty compatibility schema but cannot restore the
   removed nodes, references, operational rows, or migration diagnostics.
5. `20260822T050000-page-duplicate-attachment-pins` creates durable source
   attachment pins for page-duplication outbox work and backfills every active
   `pending`, `processing`, or `failed` item. Completed and cancelled work
   releases its pins; failed work deliberately retains them so attachment
   cleanup cannot delete the only remaining source before a retry or operator
   decision. The migration fails closed on invalid payloads or unavailable
   sources. Its down path is blocked while any pin or active duplication work
   remains.

No mandatory full search reindex is introduced by these migrations.

An installation upgrading directly from `v1.2.0` or earlier must first apply
the three `v1.2.1` migrations and complete its mandatory page, attachment, and
dictionary reindex. PostgreSQL remains authoritative; Typesense is a
rebuildable projection and is not part of the coordinated backup archive.

The production CLI now resolves supported file-backed secrets before opening
its database and Redis connections. `DATABASE_URL_FILE` and `REDIS_URL_FILE`
therefore work for console maintenance commands as they do for the application.
Configuring a direct value together with its `_FILE` form remains a startup
error rather than an implicit precedence rule.

Unconfirmed Docmost archive previews expire after 24 hours. A five-minute
reconciler first fences the pending task as failed, then removes its durable
artifact; cleanup failure remains visible for the failed-artifact reconciler
instead of losing the storage locator. Confirmation uses a competing atomic
state transition, so expiry cannot cancel an already confirmed import.

## RAG and Open WebUI fixes

- RAG export compares UUID member identifiers as text when projecting assignee
  and stakeholder fields, avoiding PostgreSQL `uuid = text` failures.
- Pending upload intents trigger reconciliation even when their cleanup flag
  was not set. Stale mappings are removed only when they still belong to the
  reconciled operation.
- Indexed PDF and DOCX attachment text is uploaded as a Markdown projection;
  TXT and Markdown retain their portable content. Binary fallback remains
  available when extracted text is not ready.
- Remote attachment names include the Docmost attachment ID, so equal source
  names cannot collide inside one Knowledge Base. Legacy attachment mappings
  are matched only within their attachment source type.
- Open WebUI `file_hash` is scoped to the upload operation while signed Docmost
  metadata retains the source content hash used for reconciliation. Identical
  content from distinct sources is no longer collapsed accidentally.
- Writer verification performs a bounded, read-only target preflight before it
  arms cleanup and starts the marker write. A preflight failure leaves a clean
  binding; an interrupted write stage retains the cleanup requirement.
- Safe writer diagnostics for policy rejection, authorization, timeouts,
  processing failures, redirects, source limits, lease loss, and cancellation
  are preserved for the administrator UI. Cleanup recovery may save a rotated
  writer key and retry sequentially without exposing the credential.

Administrators should verify the saved target, writer credential, cleanup
state, and representative attachment projections before accepting a deployment
that uses RAG Sync. A healthy base API does not prove Open WebUI compatibility.

## Search and user-interface fixes

- Dictionary search results include a plain-text definition preview and keep
  the term as the direct link to its dictionary entry.
- Synchronized-template editing distinguishes shared template-managed content
  from page-local editable fields. Linked pages keep fields editable while
  shared content remains read-only, and template authors get contextual create,
  convert, and field-settings actions.
- Subpage blocks refresh their page context after asynchronous editor creation,
  preventing stale parent-page queries.
- The AI assistant profile editor and narrow-screen composer have clearer
  responsive grouping, accessible state, and stable action sizing.
- Mobile page headers keep Edit/Read as accessible compact segments and move
  page details, comments, and table-of-contents actions into the overflow menu.
  Public sharing controls are hidden when workspace or space policy disables
  sharing.
- Initial Service Worker activation no longer reloads a fresh page merely
  because the first controller becomes available; updates still follow the
  existing version-change flow.

## Rollback boundary

Because this release changes the database schema and removes legacy data, a
pre-ingress rollback must use the production rollback operator with the
preserved pre-migration database volume and previous application image. Do not
select the previous image against the migrated schema and do not treat
`migration:down` as a data-preserving rollback.

If the deployment also crossed the `v1.2.1` migration boundary, use the matching
older preserved volume and image together. The tag-settings,
dictionary-source, durability, history, idempotency, and whole-page-embed down
paths cannot preserve all accepted data.

After ingress accepts writes on `v1.2.3`, automatic rollback is forbidden by
the deployment contract. Recovery then requires a planned forward fix or a
DBA-approved logical or point-in-time restore.

## Release evidence boundary

The release note, migration source, and matching manifests do not prove that
tag `v1.2.3` exists, that a registry image was published, or that hosted CI,
staging capacity, production migration/rollback drills, or live external
integrations passed. Record the exact tag, commit, image digest, hosted checks,
and environment-specific acceptance separately before publication or
deployment.
